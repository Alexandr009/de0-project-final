# Итоговый проект: транзакционная активность финтех-стартапа

Пайплайн собирает транзакции клиентов и курсы валют из PostgreSQL, складывает их в staging-слой
хранилища на Vertica и ежедневно считает витрину `global_metrics` — динамику оборота компании
в разрезе валют.

## Итоговая витрина

**Vertica:** `vertica.data-engineer.education-services.ru:5433`, БД `dwh`
**Витрина:** `VT260725214E22__DWH.global_metrics`

| Поле | Содержание |
|---|---|
| `date_update` | дата расчёта (день транзакций) |
| `currency_from` | код валюты транзакции |
| `amount_total` | сумма выполненных транзакций по валюте, в долларах |
| `cnt_transactions` | количество выполненных транзакций по валюте |
| `avg_transactions_per_account` | среднее число транзакций на аккаунт клиента |
| `cnt_accounts_make_transactions` | число уникальных аккаунтов клиентов с транзакциями |

Витрина заполнена за октябрь 2022 года: по строке на каждую пару «день × валюта».
DAG отработали за все 31 день октября, но данные в источнике есть не за каждый день:
транзакции встречаются в 15 днях, причём в части из них (6, 11, 19, 21, 25) только возвраты
(`chargeback`) по операциям прошлых дней. Выполненные операции есть за 10 дней —
1, 5, 8, 9, 10, 18, 20, 23, 24 и 31 октября; они и попадают в витрину. Запуски за дни без
выполненных операций проходят успешно и ничего не пишут.

## Архитектура

```
PostgreSQL db1 (источник)                 Vertica dwh
  public.transactions ──┐   1_data_import   VT260725214E22__STAGING.transactions ──┐  2_datamart_update
  public.currencies   ──┴─────────────────▶ VT260725214E22__STAGING.currencies   ──┴─────────────────▶ VT260725214E22__DWH.global_metrics
                           (Airflow, @daily)                                          (Airflow, @daily)
```

Источник — PostgreSQL: данные в нём естественно режутся по дням запросом по `transaction_dt`,
что совпадает с требованием ежедневной инкрементальной загрузки.

## Структура репозитория

| Файл | Назначение |
|---|---|
| `src/sql/ddl.sql` | таблицы staging и DWH: партиции по дню, проекции по датам с сегментацией `HASH(дата, id)` |
| `src/sql/datamart_global_metrics.sql` | расчёт витрины за день |
| `src/dags/1_data_import.py` | DAG: PostgreSQL → Vertica staging за день |
| `src/dags/2_datamart_update.py` | DAG: staging → `global_metrics` за день |

## Как работают DAG

Оба DAG — `@daily` с `catchup` за октябрь 2022 (`start_date = 2022-10-01`, `end_date = 2022-10-31`):
каждый день обрабатывается отдельным запуском, логическая дата `{{ ds }}` — это «вчера»
относительно момента запуска по расписанию.

**`1_data_import`** — две задачи, `load_transactions` и `load_currencies`. Каждая выгружает из
PostgreSQL строки за свой день и в одной транзакции Vertica удаляет этот день в staging и
загружает заново через `COPY`. После загрузки число строк сверяется с выгрузкой. Перезапуск
за любой день не создаёт дублей.

**`2_datamart_update`** — ждёт (`ExternalTaskSensor`) загрузку staging за тот же день, затем
в одной транзакции удаляет день из витрины и вставляет пересчитанный.

## Правила расчёта витрины

Решения приняты по результатам изучения данных:

- **Тестовые аккаунты исключаются** — строки, где `account_number_from < 0` или `account_number_to < 0`.
- **Учитываются только выполненные операции (`status = 'done'`), каждая один раз.** У операции в
  источнике несколько строк — по одной на каждый статус (`queued → in_progress → done`, иногда
  `blocked` и `chargeback`). Если считать все строки, одна операция попала бы в оборот 3–5 раз.
- **Аккаунт клиента — `account_number_to`.** В `account_number_from` во всех транзакциях стоит один из
  двух внутренних бухгалтерских счетов компании (`903810`, `914810`), поэтому по нему нельзя
  посчитать клиентов.
- **Сумма в долларах:** `amount` хранится в минимальных единицах валюты (центы, копейки), поэтому
  делится на 100 и умножается на курс дня к доллару (код `420`) из `currencies`. Сумма берётся по
  модулю: исходящие переводы в источнике записаны с минусом, а витрина показывает оборот.
- **`avg_transactions_per_account`** = `cnt_transactions / cnt_accounts_make_transactions`.

Особенности источника, учтённые при загрузке:
- в `public.transactions` есть 286 полных дублей строк — выгрузка идёт через `SELECT DISTINCT`;
- колонка курса в `public.currencies` называется `currency_with_div`; в staging она названа
  `currency_code_div`, как в описании задачи.

## Запуск

Инфраструктура — локальный Docker-образ Практикума. Папки `src/dags` и `src/sql` монтируются в контейнер:

```bash
docker run -d -p 8998:8998 -p 8280:8280 -p 15432:5432 \
  -v <путь к репозиторию>/src/dags:/lessons/dags \
  -v <путь к репозиторию>/src/sql:/lessons/sql \
  --name=de-final-prj-local cr.yandex/crp1r8pht0n0gl25aug1/de-final-prj:latest
```

Подключения Airflow (Admin → Connections):

| Conn Id | Тип | Параметры |
|---|---|---|
| `postgres_source` | Postgres | `rc1b-w5d285tmxa8jimyn.mdb.yandexcloud.net:6432`, БД `db1`, extra `{"sslmode": "require"}` |
| `vertica_dwh` | Vertica | `vertica.data-engineer.education-services.ru:5433`, БД `dwh` |

Таблицы создаются скриптом `src/sql/ddl.sql`, затем DAG включаются в Airflow.
